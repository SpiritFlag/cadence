## 1. 범위

코드가 후보 순서를 만들고, LLM이 그것을 의미로 묶어 패키지 다섯을 제안하고, 사용자가 승인한 라벨 변경이 GitHub에 반영된다. 오른쪽 빈 칸이 패키지 카드로 채워진다.

### 1.1 후보 순서 — #6

- 무엇을: 순환 검출만 있음 → 순수 함수가 열린 이슈와 의존 선을 받아 후보 순서 · 순환 · 승격 제안을 돌려준다. 막는 것이 앞(위상 정렬). 같은 층은 `p1` → `p2` → `p3`. `hold`는 순서에서 뺀다. 라벨이 없으면 `p3`, 둘 이상이면 높은 것. 막히는 쪽이 막는 쪽보다 높으면 막는 쪽을 같은 라벨로 올리자는 제안을 낸다(내리는 제안은 없다. 사슬을 따라 전파한다). 순환이 있으면 순서 대신 순환 선 목록. 패키지 검사 함수 하나: 패키지 목록을 받아 사슬 보존(막는 쪽이 같은 패키지거나 앞) · 이슈 누락 · 크기 상한 5를 검사해 경고 목록을 낸다.
- 어떻게: `server/graph/order.ts` 하나. 플레인 TS. API는 붙이지 않는다. 1.2가 서버 안에서 쓴다.
- 끝(SC-1): `bun test server/graph`로 사슬 순서 · 같은 층 라벨 순 · hold 제외 · 라벨 없음은 p3 · 둘 이상이면 높은 것 · 순환이면 순서 없음 · 승격 제안(전파 포함) · 내리는 제안 없음 · 패키지 검사 셋 — `bun test`. 육안 없음.
- 왜 이렇게: 결정적인 것은 코드가 하고 테스트로 못 박는다(`docs/design.md` 분담 표). 승격 전파는 "C가 급하면 C를 막는 것도 급하다"가 비서의 상식이라서. 한 단계만 하면 사슬 앞이 낮은 채로 남는다.

### 1.2 제안 — #7

- 무엇을: 오른쪽 빈 칸 → 패키지 카드. 헤더의 [제안]을 누르면 서버가 `claude -p`를 자식 프로세스로 부른다(도구 없음 · `--bare` · 스키마 강제 · 세션 저장 안 함 · 호출당 예산 상한). 열린 이슈(레포 · 번호 · 제목 · 본문 · 라벨) + 의존 선 + 후보 순서 + 규칙을 넘겨 패키지 목록 JSON(순위 · 이름 · 이슈들 · 이유 · 라벨 변경 제안)을 받는다. 검사 함수로 검증해 어긴 패키지에 경고를 붙인다. `proposals`에 저장되어 다시 켜도 마지막 제안이 보인다. 카드는 5장, 그 이하는 "그 외 N개"로 접힌다. 카드에 마우스를 올리면 그 이슈들이 그래프에서 강조된다. 순환이 있으면 버튼이 비활성이고 이유가 보인다. JSON이 깨지면 한 번 재시도, 또 깨지면 "제안 없음" 상태로 후보 순서만 카드 하나에 보인다.
- 어떻게: `server/llm/claude.ts`(spawn 한 겹, 주입 가능한 `Proposer`) · `server/propose/`(프롬프트 조립 · 검증 · 저장 · 최근 조회) · 마이그레이션 003 `proposals` · 라우트 `POST /api/propose` · `GET /api/proposals/latest`. 프론트는 store에 `proposal` · `highlight`, `Packages.svelte` · `PackageCard.svelte`, Graph가 강조를 노드에 반영. 모델은 정하지 않는다. `claude`는 PATH에서 찾고 없으면 `CADENCE_CLAUDE`.
- 끝(SC-2): `bun test server/propose`로 가짜 proposer 기준 — 프롬프트에 후보 순서와 규칙이 들어간다 · 어긴 출력에 경고가 붙는다 · 저장 후 최근 조회 · 깨진 JSON은 한 번 재시도 뒤 "없음" · 순환이면 proposer를 부르지 않는다 — `bun test`. 사용자 육안 — [제안]을 누르면 몇 초 뒤 카드가 뜨고 이름 · 이슈 칩 · 이유 · 라벨 변경 제안이 보이고, 카드에 마우스를 올리면 그래프 노드가 강조되고, 다시 켜도 제안이 남아 있다.
- 왜 이렇게: `docs/design.md` LLM 층 · 스케줄링 절 그대로. `--json-schema`로 CLI 쪽에서 스키마를 강제하면 파싱 실패가 거의 없어진다. **`docs/SPEC.md` 화면 절의 "오른쪽 패키지 자리(비어 있음)"가 패키지 카드로 바뀐다.** `claude` CLI가 PATH에 없어 사용자 허락 뒤 `npm i -g @anthropic-ai/claude-code`로 깐다.

### 1.3 반영 — #8

- 무엇을: 라벨 변경 제안이 카드 안에만 있음 → 항목마다 체크(기본 켜짐)가 있고 [승인한 라벨 변경 반영]을 누르면 체크 남은 건만 서버로 간다. 서버는 건마다 지금 라벨을 다시 읽어 제안 당시와 다르면 건너뛰고, 같으면 `gh issue edit --add-label --remove-label`로 바꾸고, gh가 실패하면 그 건만 실패로 두고 나머지를 계속한다. 결과 목록(반영 · 건너뜀 · 실패)이 보이고 성공한 건은 동기화를 다시 해 뱃지가 바뀐다. 쓰는 라벨은 `p1` `p2` `p3` `hold` 넷뿐.
- 어떻게: `server/github/gh.ts`에 라벨 읽기 · 쓰기 함수, 주입 가능. `server/apply/` 모듈이 건별 루프. 라우트 `POST /api/apply`. 프론트는 카드 체크박스 · store에 `applyResult` · Packages 하단 버튼.
- 끝(SC-3): `bun test server/apply`로 가짜 gh 기준 — 정상 건 반영 · 제안 당시와 다르면 건너뜀 · 한 건 실패해도 나머지 진행 · 넷 밖 라벨은 쓰지 않음 · 반영 뒤 동기화 — `bun test`. 사용자 육안 — 실제 제안에서 승격 하나를 반영하면 GitHub 웹에서 라벨이 바뀌어 있고 화면 뱃지도 바뀐다. GitHub 웹에서 손으로 되돌린 뒤 같은 제안을 다시 반영하면 건너뜀이 뜬다.
- 왜 이렇게: `docs/design.md` "GitHub에 쓰는 것은 우선순위 라벨뿐" · 어긋난 경우 표 그대로. 반영 직전 재확인은 제안이 오래된 것일 수 있어서. 부분 실패를 롤백하지 않는 것은 gh 쓰기가 건별 원자라 롤백이 또 다른 쓰기이기 때문.

제외: 주기 폴링 · 제안 자동 실행 · 여러 제안 이력 보기(마지막 것만) · 마크다운 렌더링.
