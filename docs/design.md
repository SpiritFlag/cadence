# 설계

cadence의 설계 근거. README는 "뭐고 어떻게 깔고 뭘 치나"까지만 답하고, 왜 이렇게 만들었는지는 여기에 적는다. 지금 어떻게 동작하는지는 `docs/SPEC.md`(있을 때).

## 스택

| 층 | 선택 | 근거 |
|---|---|---|
| 런타임 | Bun | TypeScript를 빌드 없이 실행한다. sqlite · 테스트 러너 · HTTP 서버가 내장이라 의존성이 최소다 |
| 서버 | Hono | 라우트가 적은 로컬 앱에 맞는 크기. Bun 위에서 바로 돈다 |
| DB | sqlite (`bun:sqlite`) | 로컬 단일 파일. ORM 없이 SQL 파일을 번호순으로 적용해 마이그레이션한다 |
| GitHub | `gh` CLI를 자식 프로세스로 호출 | 인증을 gh가 갖고 있어 토큰을 저장하지 않는다. `--json`으로만 읽는다 |
| 프론트 | Svelte 5 + Vite | 대시보드는 상태가 많다. 코드 양이 적어 혼자 유지하기 좋다 |
| 그래프 | @xyflow/svelte + dagre | 노드가 Svelte 컴포넌트라 이슈 카드(번호 · 제목 · 라벨 · 제안 표시)를 그대로 쓴다. 좌표는 dagre가 계산한다 |
| 검증 | `bun test` · `svelte-check` | 런타임에 딸려 오는 것만 쓴다 |

### 버린 길

- **Node + better-sqlite3 + vitest** — 성능 차이는 이 앱에서 의미가 없다. 도구를 세 개 따로 고르는 대신 하나에 딸린 것을 쓴다.
- **HTMX + 서버 렌더** — 프론트 빌드가 없어 가볍지만, 그래프 위에서 드래그 · 클릭으로 우선순위를 바꾸는 것이 핵심 흐름이라 클라이언트 상태가 필요하다.
- **GitHub API 직접 호출** — 토큰 관리가 생긴다. gh가 이미 로그인돼 있는 환경을 전제로 한다.
- **Cytoscape.js** — 레이아웃과 인터랙션이 내장이지만 노드가 도형+텍스트라 카드 형태로 꾸미기 어렵다.
- **viz.js(Graphviz) · Mermaid** — 정적 그림이라 선 긋기 · 클릭이 안 된다.

## 의존 관계는 로컬에만 둔다

GitHub는 이슈 목록의 원본이고, 이슈 사이의 의존 관계(무엇이 무엇을 막는가)는 cadence의 sqlite에만 있다. 사용자가 대시보드에서 선을 긋고, 그 선으로 토폴로지를 그린다. GitHub에는 이 관계를 쓰지 않는다.

- 사용자는 이 도구를 혼자 로컬에서 쓴다. GitHub 쪽에 남아야 하는 것은 이슈 목록으로 충분하다.
- 파싱 규칙이 없다. 본문에 어떤 관습을 강요하지 않는다.
- 대가: 머신을 옮기면 관계가 따라오지 않는다. sqlite 파일을 옮기는 것으로 감당한다.

### 버린 길

- **이슈 본문의 `blocked by #n` 관습 파싱** — GitHub 웹에서도 보인다는 장점이 있지만, 파싱 규칙이 곧 스펙이 되고 오타 하나에 끊긴다.
- **GitHub 네이티브 의존성(Blocked by)** — `gh issue view --json`이 내주지 않아 GraphQL을 따로 쳐야 하고, 플랜 제약이 있을 수 있다.

## GitHub에 쓰는 것은 우선순위 라벨뿐이다

동기화는 GitHub → cadence가 기본이다. cadence가 GitHub에 쓰는 것은 `p1` `p2` `p3` `hold` 라벨의 변경뿐이다. 본문 · 제목 · 상태 · 코멘트는 쓰지 않는다.

- 우선순위는 cycle 체계가 GitHub 라벨로 읽는다. cadence가 조율한 결과가 라벨로 남아야 `/cycle:start`와 한 몸이 된다.
- 쓰기 범위가 라벨 넷으로 닫혀 있어 잘못 써도 피해가 작고 되돌리기 쉽다.
- 쓰기 명령은 `gh issue edit --add-label` · `--remove-label`뿐이다.

### 버린 길

- **읽기 전용** — 가장 단순하지만, cadence 화면의 우선순위와 GitHub 라벨이 따로 놀아 사용자가 손으로 옮겨야 한다.

## 조율은 순서 제안이다

cadence는 토폴로지와 현재 라벨을 보고 "다음에 할 것"의 순서와 라벨 변경을 제안한다. 사용자가 승인하면 라벨 변경을 GitHub에 반영한다. 보여주기만 하거나 어긋남만 경고하는 것으로는 비서가 아니다.

### 제안 규칙 (초안)

1. **막는 것이 앞이다.** A가 B를 막으면 A가 B보다 앞에 온다(위상 정렬). 순환이 있으면 제안하지 않고 순환을 표시한다.
2. **같은 층에서는 라벨 순이다.** `p1` → `p2` → `p3`. `hold`는 순서에서 뺀다.
3. **어긋남은 승격으로 푼다.** B가 `p1`인데 B를 막는 A가 `p2` 이하이면, A를 B와 같은 라벨로 올리자고 제안한다. 내리는 제안은 하지 않는다.
4. **제안은 라벨 변경 목록이다.** 사용자가 목록을 보고 항목별로 승인 · 제외한 뒤 한 번에 반영한다. 반영은 `gh issue edit`뿐이다.

규칙은 실제로 써보며 바꾼다. 바뀐 규칙은 `docs/SPEC.md`가 정본이 된다.

## 기본값

- **대상 레포**: 사용자가 화면에서 `owner/name`을 추가한다. 여러 개일 수 있다. sqlite에 저장한다.
- **동기화 시점**: 앱을 켤 때와 사용자가 새로고침을 누를 때. 주기 폴링은 하지 않는다.
- **닫힌 이슈**: 그래프에서 빼되 sqlite에는 남긴다. 의존 선이 끊기지 않게 한다.
