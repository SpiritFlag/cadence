# 설계

cadence의 설계 근거. README는 "뭐고 어떻게 깔고 뭘 치나"까지만 답하고, 왜 이렇게 만들었는지는 여기에 적는다. 지금 어떻게 동작하는지는 `docs/SPEC.md`(있을 때).

## 스택

| 층 | 선택 | 근거 |
|---|---|---|
| 런타임 | Bun | TypeScript를 빌드 없이 실행한다. sqlite · 테스트 러너 · HTTP 서버가 내장이라 의존성이 최소다 |
| 서버 | Hono | 라우트가 적은 로컬 앱에 맞는 크기. Bun 위에서 바로 돈다 |
| DB | sqlite (`bun:sqlite`) | 로컬 단일 파일. ORM 없이 SQL 파일을 번호순으로 적용해 마이그레이션한다 |
| GitHub | `gh` CLI를 자식 프로세스로 호출 | 인증을 gh가 갖고 있어 토큰을 저장하지 않는다. `--json`으로만 읽는다 |
| 프론트 | Svelte 5 + Vite | 대시보드는 상태가 많다. 코드 양이 적어 혼자 유지하기 좋다 |
| 그래프 | Cytoscape.js | 토폴로지 레이아웃과 노드 인터랙션이 내장이다 |
| 검증 | `bun test` · `svelte-check` | 런타임에 딸려 오는 것만 쓴다 |

### 버린 길

- **Node + better-sqlite3 + vitest** — 성능 차이는 이 앱에서 의미가 없다. 도구를 세 개 따로 고르는 대신 하나에 딸린 것을 쓴다.
- **HTMX + 서버 렌더** — 프론트 빌드가 없어 가볍지만, 그래프 위에서 드래그 · 클릭으로 우선순위를 바꾸는 것이 핵심 흐름이라 클라이언트 상태가 필요하다.
- **GitHub API 직접 호출** — 토큰 관리가 생긴다. gh가 이미 로그인돼 있는 환경을 전제로 한다.

## 의존 관계는 로컬에만 둔다

GitHub는 이슈 목록의 원본이고, 이슈 사이의 의존 관계(무엇이 무엇을 막는가)는 cadence의 sqlite에만 있다. 사용자가 대시보드에서 선을 긋고, 그 선으로 토폴로지를 그린다. GitHub에는 이 관계를 쓰지 않는다.

- 사용자는 이 도구를 혼자 로컬에서 쓴다. GitHub 쪽에 남아야 하는 것은 이슈 목록으로 충분하다.
- 파싱 규칙이 없다. 본문에 어떤 관습을 강요하지 않는다.
- 대가: 머신을 옮기면 관계가 따라오지 않는다. sqlite 파일을 옮기는 것으로 감당한다.

### 버린 길

- **이슈 본문의 `blocked by #n` 관습 파싱** — GitHub 웹에서도 보인다는 장점이 있지만, 파싱 규칙이 곧 스펙이 되고 오타 하나에 끊긴다.
- **GitHub 네이티브 의존성(Blocked by)** — `gh issue view --json`이 내주지 않아 GraphQL을 따로 쳐야 하고, 플랜 제약이 있을 수 있다.
